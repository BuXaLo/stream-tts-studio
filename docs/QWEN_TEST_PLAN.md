# План экспериментальной сборки Qwen3-TTS для Stream TTS Studio

**Статус на 2026-11-15:** этапы A и C выполнены; автономная загрузка Codec и Zero-Shot генерация Qwen3-TTS 1.7B Base Q8_0 на RTX 5080 успешно проверены. Выявлена нестабильность окончания некоторых фраз; причина и варианты коррекции исследуются. HTTP-сервис, отдельный Python runtime, перенос runtime и адаптация Studio ещё не выполнялись.  
**Экспериментальная ветка:** `qwen_test`  
**База ветки:** `dev_test` — `824b2d9c5c3743a4748cf42c5c84ff23e27bd5f7`  
**Движок:** [qwentts.cpp](https://github.com/ServeurpersoCom/qwentts.cpp)  
**Цель:** собрать в отдельной папке независимое окружение Qwen3-TTS 1.7B, затем перенести поверх него копию Studio и адаптировать её отдельно, сохранив текущую CosyVoice-сборку нетронутой.

---

## 1. Принципы и границы эксперимента

1. Это параллельный эксперимент, а не замена текущего CosyVoice 3.
2. Не изменять существующую рабочую сборку, её portable Python, модели, CUDA/PyTorch и runtime.
3. Новую сборку разворачивать в отдельной папке с нуля.
4. Не копировать Python-пакеты из текущего окружения. Установить отдельный CPython и свежие совместимые зависимости.
5. Сначала проверить движок и вспомогательные инструменты автономно. Только после этого переносить код Studio.
6. Адаптацию Studio выполнять в ветке `qwen_test`, не смешивая её с основной разработкой.
7. Сохранять существующие внешние контракты и интеграции: `POST /speak`, WAV, WebSocket `/ws/overlay`, OBS Browser Source, C# для Streamer.bot, OAuth DonationAlerts, конфиги и форматы пользовательских данных.
8. Не переносить CosyVoice, PyTorch, torchaudio и Demucs, если отдельная проверенная необходимость не появится.
9. Не фиксировать версии зависимостей и оборудования на основании предположений. Перед установкой сверить актуальные требования проектов и совместимость пакетов.

**Окружение для фактической сборки:** первая попытка CMake выполнялась из x86 prompt (`VSCMD_ARG_HOST_ARCH=x86`, `VSCMD_ARG_TGT_ARCH=x86`, `Hostx86\\x86\\cl.exe`) и завершилась ошибкой CUDA compiler identification / `cudafe++` Access Violation. Повторная конфигурация в отдельном каталоге `build-cuda-x64` прошла успешно. Причина первоначального сбоя была в неверно активированном x86 окружении; менять CUDA Toolkit или драйвер не потребовалось.

**Выбор MSVC для сборки:** CUDA-сборку выполнять из Developer Command Prompt Visual Studio 2022, где активен MSVC 19.44.35230. MSVC 19.52.37029 из Visual Studio 2026 с CUDA 13.0 не использовать: обычная проверка версии компилятора завершилась ошибкой, а обход через `-allow-unsupported-compiler` привёл к падению `cudafe++` с Access Violation. Этот флаг для рабочей сборки не применять.

Visual Studio 2026 оставлена установленной, но для текущей CUDA-сборки используется VS 2022. На основании успешного probe-теста обновление NVIDIA Driver или установка CUDA 13.2 сейчас не требуются.

У qwentts.cpp есть Windows build scripts, но перед запуском проверить жёстко заданные в них пути к Visual Studio/CUDA. Если скрипт не соответствует установленной конфигурации, использовать документированную конфигурацию CMake без внесения ненужных изменений в исходники движка.

**Обнаруженная проблема: нестабильное окончание фраз**

Иногда Qwen произносит фразу полностью, иногда резко обрывает последнюю букву или окончание. Проблема проявляется не на каждом запуске.

По исходникам qwentts.cpp на commit `f1a6924789883bd92eeb59176793a94af55730b3` установлено:
- в `src/pipeline-tts.cpp` специальный `codec_eos_id` оставлен разрешённым при выборке Talker на каждом шаге;
- при выборе EOS генерация немедленно завершается, новый аудиокадр не создаётся;
- частота генерации — 12.5 кадров/с, один кадр примерно 80 ms;
- `--max-new` по умолчанию равен 2048 кадрам и является верхним пределом, а не способом продолжить генерацию после EOS;
- seed по умолчанию `-1`, то есть запуск недетерминированный;
- `--greedy` меняет sampling и для Talker, и для Subtalker, поэтому не считается готовым исправлением.

В buffered-пути завершения накопленные `all_codes` передаются в Codec decode и затем в WAV. Явной потери последнего блока в изученном участке не обнаружено. Полный аудит streaming/final flush ещё не проводился.

**Сопоставление с CosyVoice:** в `server/studio/services/tts_engine.py` основной сборки обнаружены разбиение текста на предложения, добавление конечной точки при её отсутствии, удаление DC и fade-in/fade-out по 10 ms, а также пауза 80 ms между предложениями. Fade-out сглаживает край аудиосигнала, но не восстанавливает фонему, которую модель не сгенерировала. Эффект сегментации и пунктуации на Qwen пока не проверен.

**Следующая диагностика (не выполнена):**
1. Повторить одну и ту же фразу с одним референсом несколько раз с фиксированным `--seed 42`, сохранив логи и WAV.
2. Затем сравнить другой seed (например, 43) и обычный недетерминированный запуск.
3. Сопоставить `EOS at step N`, `Generation done N frames` и последние 300–500 ms WAV.
4. Определить, отсутствует ли часть фонемы или слышен только резкий край уже завершённого аудио.
5. Отдельно проверить влияние завершающей пунктуации и генерации по предложениям.

**Возможные меры после диагностики, пока не реализованы:**
- DC removal и короткий fade-out готового WAV — только для смягчения резкого края;
- короткая конечная тишина — только если проблема связана с восприятием завершения воспроизведения;
- изменение минимального числа кадров до разрешения EOS — экспериментально и с осторожностью: может добавить лишний звук или речь;
- не менять sampling и не вводить EOS-порог до получения сравнительных результатов.

**Критерий этапа D:** базовая автономная загрузка моделей, работа Codec на CUDA и Zero-Shot генерация русской речи подтверждены. Исследование нестабильных окончаний остаётся отдельной задачей качества.

- удаление голоса через `DELETE /v1/audio/voices/{name}`;
- синтез через `POST /v1/audio/speech`.

Проверить:
- обычный WAV-ответ;
- потоковый режим и формат PCM, если он нужен для дальнейшей интеграции;
- повторное использование зарегистрированного голоса;
- поведение после перезапуска сервера;
- сериализацию нескольких запросов и обработку ошибок;
- время загрузки модели, время регистрации голоса, задержку до первого аудиофрагмента, полное время генерации;
- RAM и VRAM в простое и под нагрузкой.

Уточнить фактическое поведение хранения голосов в текущей версии сервера. Если регистрации хранятся только в памяти процесса, предусмотреть повторную регистрацию при запуске.

**Критерий готовности:** локальный HTTP API стабильно принимает запросы и возвращает пригодный WAV.

### Этап F. FFmpeg и Faster-Whisper

**FFmpeg**

- Установить отдельный Windows build в `runtime/tools/`.
- Не использовать FFmpeg из старой сборки.
- Проверить версию, кодеки и основные команды, которые использует Studio.

**Faster-Whisper**

**Критерий готовности:** FFmpeg выполняет аудиооперации, Faster-Whisper распознаёт речь на CPU в новом окружении.

## 5. Русская текстовая нормализация

В эксперимент включить только один внешний текстовый нормализатор — **ru-normalizr**: [NickZaitsev/ru-normalizr](https://github.com/NickZaitsev/ru-normalizr).

Исключить из плана:
- rutextnorm;
- RUAccent;
- отдельную автоматическую расстановку ударений.

Задача эксперимента — сравнить внешний текстовый нормализатор с уже имеющейся встроенной нормализацией Studio. Не считать заранее, что внешний вариант лучше.

Подготовить единый набор тестовых фраз из реальных сценариев стрима:
- целые и дробные числа;
- даты и время;
- суммы и валюты;
- проценты и единицы измерения;
- сокращения;
- URL и латиница;
- обычные фразы и длинные сообщения.

Для каждой фразы сохранить три варианта:
1. исходный текст;
2. результат встроенной нормализации Studio;
3. результат ru-normalizr.

Сравнить преобразования и прослушать синтез обоих нормализованных вариантов на одном движке и одном голосе. Проверить поддержку пользовательских правил/словарей и возможность отключения нормализатора.

**Критерий готовности:** принято обоснованное решение — оставить встроенную нормализацию, заменить её либо использовать внешний нормализатор как дополнительный этап.

## 6. Совместимость WAV-конвертации

Текущий Studio helper `convert_to_clean_wav()` приводит аудио к:

- WAV;
- mono;
- 24 kHz;
- PCM signed 16-bit.

Предварительно этот формат подходит для входного референса Qwen. При этом qwentts.cpp умеет принимать ряд других WAV-форматов и самостоятельно приводить вход к внутреннему формату. Поэтому предварительная конвертация для самого Qwen может быть необязательной.

На первом этапе не менять существующий helper. Провести сравнение трёх вариантов на одинаковых исходниках:

1. WAV после текущего `convert_to_clean_wav()`;
2. исходный WAV без предварительной конвертации;
3. WAV, преобразованный FFmpeg напрямую по параметрам, рекомендованным текущей версией qwentts.cpp.

Проверить:
- mono и stereo;
- стерео, где голос присутствует только в правом канале;
- разные частоты дискретизации;
- PCM16 и поддерживаемые движком альтернативные форматы;
- тихие и громкие референсы;
- длительность, обрезку, клиппинг и качество клонирования.

**Предварительное решение:** сохранить текущую конвертацию как общий канонический формат для сопоставимого тестирования CosyVoice и Qwen. Отказываться от неё только если тесты покажут измеримую пользу прямой подачи исходного файла.

## 12. План очистки от временных и лишних файлов

Очистку выполнять только после успешного запуска движка, проверки CUDA backend и фиксации контрольных сумм рабочих артефактов. До этого ничего не удалять: промежуточные каталоги могут понадобиться для диагностики.

### 12.1. Что можно будет удалить после подтверждения успешной x64-сборки

- `build\qwentts.cpp\build-cuda\` — каталог первой неудачной конфигурации из x86-окружения. Он содержит устаревший CMake cache и не используется успешной сборкой `build-cuda-x64`.
- Временные CUDA probe-файлы из `%TEMP%` (например, `cuda_probe.cu` и `cuda_probe.exe`), если они больше не нужны для диагностики и результат `CUDA TEST PASSED: 42` уже сохранён в документации.
- Временные логи, промежуточные тестовые WAV и дубликаты скачанных архивов — только после сохранения нужных эталонных входов/выходов и результатов тестов.

### 12.2. Что можно будет удалить после переноса и полного тестирования runtime

- `build\qwentts.cpp\build-cuda-x64\` и прочие generated build artifacts — только после того, как рабочие EXE/DLL перенесены в `runtime\qwentts\bin`, их SHA256 записаны, запуск и генерация проверены, а повторная сборка не требуется в ближайшем цикле. Если важна воспроизводимость без повторной компиляции, оставить build-каталог до отдельного решения.
- Неиспользуемые промежуточные файлы компиляции и временные каталоги, оставшиеся внутри build-каталога, удалять вместе с ним, а не вручную из исходников.
- Неиспользуемые варианты GGUF и тестовые аудиофайлы — только после выбора финальной модели и сохранения небольшого набора воспроизводимых тестовых референсов.

### 12.3. Что не удалять в рамках этой очистки

- `build\qwentts.cpp\` как каталог исходников, `.git` и содержимое GGML submodule: они нужны для фиксации версий и повторной сборки.
- Рабочие EXE/DLL в `runtime\qwentts\bin`, выбранные GGUF в `runtime\qwentts\models`, отдельный Python/venv, FFmpeg и другие используемые инструменты.
- Пользовательские данные Studio: персонажи, референсы, пресеты, настройки, история и необходимые логи.
- CUDA Toolkit, NVIDIA Driver и Visual Studio Build Tools автоматически не удалять. То, что VS 2026 не использовалась для этой сборки, само по себе не является основанием для деинсталляции.
- Не удалять и не менять старое окружение CosyVoice.

### 12.4. Порядок безопасной очистки

1. Проверить запуск всех трёх EXE и фактическую загрузку CUDA backend.
2. Проверить генерацию на выбранных GGUF и сохранить эталонные входы/выходы.
3. Перенести подтверждённые файлы в `runtime\qwentts\bin`; вычислить и записать SHA256 каждого EXE/DLL.
4. Проверить запуск уже из `runtime\qwentts\bin`, не полагаясь на текущий рабочий каталог сборки и случайные пути из Developer Command Prompt.
5. Удалить только явно ненужный неудачный `build-cuda` и временные файлы.
6. Решение об удалении `build-cuda-x64` принять отдельно после проверки повторяемости и необходимости хранить артефакты сборки.

**Критерий завершения очистки:** рабочий runtime запускается независимо от каталога исходников; исходники и зафиксированные SHA остаются доступными для воспроизводимой сборки; пользовательские данные и старое CosyVoice-окружение не затронуты.
