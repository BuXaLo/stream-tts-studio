# Диагностика и безопасная оптимизация использования GPU/VRAM

> Статус: исследование завершено (2026-11-15). Доказанного безопасного резерва для оптимизации не найдено; изменения приложения и runtime не требуются.

## 1. Цель

Выяснить, можно ли уменьшить лишнее потребление видеопамяти Stream TTS Studio в простое и после генераций, не ухудшая готовность к стриму, скорость и качество синтеза.

Цель — не минимизировать цифру VRAM любой ценой, а найти и устранить только доказанный лишний расход памяти.

## 2. Неизменяемые условия

- Модель CosyVoice загружается в GPU при запуске Studio и остаётся там всё время работы приложения.
- Прогрев модели перед стримом сохраняется.
- Не допускаются выгрузка модели из GPU в простое, отложенная загрузка и повторная загрузка перед донатом.
- Не допускаются изменения, увеличивающие время первой генерации после запуска или простоя.
- Не менять веса, точность вычислений, n_timesteps, скорость, чанкинг и другие параметры синтеза.
- Не менять версии Python, CUDA, PyTorch, CosyVoice, ML-библиотек и модели; не модифицировать portable runtime.
- Не менять /speak, формат и содержимое WAV, WebSocket /ws/overlay, OBS Browser Source, DonationAlerts, generated C# Actions, конфиги и пользовательские данные.
- Не внедрять и не тестировать экспериментальные изменения во время эфира.

## 3. Что уже известно

### 3.1. По коду приложения

По состоянию изученного dev_test:

- server/app.py загружает CosyVoice при старте через load_cosyvoice_model(COSY_PATH).
- Объект модели передаётся в TTS engine и хранится в глобальном состоянии процесса.
- Генерация выполняется под generation_lock и в torch.inference_mode().
- После генерации вызывается clear_vram(), которая делает torch.cuda.empty_cache() при доступной CUDA и gc.collect().
- empty_cache() освобождает неиспользуемые блоки кэша PyTorch, но не память живых тензоров и не веса загруженной модели.

Это описание конкретного изученного состояния исходников. Перед реализацией любого изменения исходные файлы необходимо перечитать из актуального dev_test.

### 3.2. Что пока неизвестно

До первого измерительного прогона не было сопоставимых замеров VRAM. По результатам этапа 1 получен первичный baseline (см. раздел 4.4), но пока не установлено:

- сколько памяти занимает сама модель после загрузки;
- сколько занимают другие постоянные CUDA-объекты и сторонние компоненты;
- остаются ли после генерации живые временные CUDA-тензоры;
- насколько меняются allocated/reserved и process-level VRAM после прогрева и простоя;
- есть ли заметный расход, который можно безопасно устранить без изменения синтеза.

Наличие локальных переменных с результатами генерации рядом с вызовом clear_vram() само по себе не доказывает утечку или удержание значимого объёма памяти. Это повод проверить время жизни объектов, а не готовый диагноз.

### 3.3. Исторические показатели скорости

Ранее владелец предоставил три измерения генерации на RTX 5080: 4,31 с для аудио 6,28 с; 6,04 с для аудио 10,40 с; 6,26 с для аудио 8,76 с. Расчётный RTF — примерно 0,69; 0,58; 0,71.

Эти значения — исторический ориентир скорости, а не baseline VRAM и не гарантированный критерий для иных текстов, персонажей или условий.

## 4. Этап 1 — измерить исходное состояние (без изменения кода)

### 4.1. Контрольные состояния

Снять показатели в следующем порядке, не перезапуская Studio между состояниями, если это не требуется для отдельного чистого прогона:

1. До запуска Studio — общий фон GPU и список процессов.
2. После запуска Studio и завершения загрузки модели, до первой генерации.
3. После первой прогревающей генерации.
4. После второй прогревающей генерации.
5. После обычной генерации.
6. Через 5 минут простоя.
7. Через 15 минут простоя.
8. После серии из 5–10 последовательных генераций.
9. После завершения серии и ещё 5 минут простоя.

Для воспроизводимости записывать время, текст/персонажа или использовать один и тот же тестовый набор, длительность аудио, длительность синтеза и состояние других GPU-приложений. Не запускать параллельно тяжёлые GPU-задачи.

### 4.2. Какие показатели собирать

Системный уровень (nvidia-smi):

- общая занятость VRAM GPU;
- память, приписанная процессу Studio/Python;
- другие процессы, потребляющие VRAM;
- загрузка GPU, если доступна.

Уровень PyTorch:

- torch.cuda.memory_allocated();
- torch.cuda.memory_reserved();
- torch.cuda.max_memory_allocated() для пика отдельного прогона, если его можно сбрасывать и снимать без влияния на генерацию;
- при необходимости — torch.cuda.mem_get_info() как дополнительный общий показатель свободной/общей памяти устройства.

Показатели PyTorch не равны полной VRAM процесса: CUDA-контекст и сторонние библиотеки могут выделять память вне allocator PyTorch. Поэтому их всегда сопоставлять с nvidia-smi.

### 4.3. Автоматизированный сбор на Windows

Для первого прохода добавлен одноразовый PowerShell-сборщик: [tools/collect_gpu_baseline.ps1](../tools/collect_gpu_baseline.ps1).

Порядок запуска:

1. Закрыть Stream TTS Studio.
2. Запустить PowerShell в папке репозитория/распакованного проекта и выполнить:
   powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\collect_gpu_baseline.ps1
3. Следовать подсказкам скрипта. Он попросит запустить Studio и нажимать Enter после загрузки модели, двух прогревочных генераций, одной обычной генерации и серии из 5–10 генераций.
4. Во время двух окон простоя (15 минут после обычной генерации и 5 минут после серии) скрипт сам выдерживает время и снимает контрольные точки на 5-й/15-й минутах.
5. По завершении отправить созданный файл gpu_baseline_ГГГГММДД_ЧЧММСС.txt. Он сохраняется рядом со скриптом.

Скрипт собирает время снимка, модель GPU, версию драйвера, общую/занятую/свободную VRAM, загрузку GPU, доступный список compute-процессов nvidia-smi, а также имена/PID/Working Set подходящих Windows-процессов. Полные командные строки процессов и содержимое конфигов/токенов не читаются.

**Ограничения первого прохода:** скрипт не внедряется в Python-процесс Studio и поэтому не считывает torch.cuda.memory_allocated/reserved. В режиме Windows WDDM запрос списка compute-процессов nvidia-smi может быть недоступен; это будет отмечено в отчёте. Системные показатели всё равно собираются. Эти ограничения подтвердились в отчёте 2026-11-15. Повторять этот сценарий или внедрять дополнительный сбор allocator metrics не планируется: по результатам исследования нет подтверждённой проблемы, оправдывающей дальнейшую диагностику.

Не запускать сбор во время эфира. На время измерения не выполнять другие тяжёлые GPU-задачи и не закрывать Studio до завершения всех контрольных точек.

**Фактический прогон 2026-11-15:** отчёт владельца `gpu_baseline_20261115_192503.txt`; GPU NVIDIA GeForce RTX 5080, 16 303 MiB, драйвер 580.88. Измерения выполнены сборщиком `tools/collect_gpu_baseline.ps1`. Колонки VRAM процесса и PyTorch allocator оставлены пустыми: сборщик первого этапа не внедряется в процесс Studio и эти значения не получает.

**Интерпретация и ограничения:**
- Загрузка модели увеличила общую занятость VRAM примерно на 3 787 MiB относительно исходного фона.
- После прогрева и обычной генерации общий показатель стабилизировался около 9 984–10 013 MiB в простое.
- После серии генераций и пяти минут простоя осталось около 133 MiB сверх снимка после 15 минут обычного простоя. Один прогон не позволяет определить, являются ли эти MiB кэшем allocator, живыми тензорами, контекстом CUDA или колебанием внешних процессов.
- Исходные 6 044 MiB до запуска Studio означают, что фон не был чистым. В WDDM `nvidia-smi` не предоставил надёжную атрибуцию памяти отдельным процессам; поэтому общую VRAM нельзя приписать одной Studio.
- Отчёт не доказывает утечку и не даёт оснований менять `clear_vram()`, модель или параметры синтеза.
- В отчёте есть системные показатели и Working Set Python; Working Set — системная RAM, не VRAM.

**Выход этапа:** получен первичный baseline по общей VRAM. Process-level VRAM и `torch.cuda.memory_allocated()/memory_reserved()` не собраны. Это ограничение зафиксировано; дальнейший этап диагностики закрыт без внедрения оптимизаций.



## 5. Итоги аудита и принятое решение

**Итог на 2026-11-15: исследование закрыто; оптимизация не выполняется.**

### 5.1. Жизненный цикл результата TTS

В изученном коде приложения переменная цикла `result` сохраняет ссылку на последний словарь результата до выхода из функции. Это было зафиксировано характеристическим тестом через `weakref`. Сам факт существования ссылки не доказывает удержание значимого объёма VRAM.

В upstream CosyVoice 3 изученная реализация `tts()` переносит выходной `tts_speech` на CPU перед выдачей результата. Поэтому предположение, что последний словарь обязательно удерживает CUDA-тензор во время `clear_vram()`, не подтверждено для upstream-кода. Локальный portable runtime находится вне Git и не был отдельно проверен; его поведение нельзя автоматически приравнивать к upstream.

Тесты `tests/test_tts_engine_gpu_lifecycle.py` фиксируют время жизни ссылок в тестовой модели и проверяют объединение нескольких результатов TTS в WAV. Они не измеряют реальную CUDA-память и не являются доказательством утечки.

### 5.2. Результаты измерений

Первичный прогон на RTX 5080 от 2026-11-15 приведён в разделе 4.4. Общая занятость VRAM после загрузки модели выросла примерно на 3 787 MiB; в простое после прогрева показатель находился около 9 984–10 013 MiB. После серии генераций и пяти минут простоя осталось около 133 MiB сверх снимка после обычного простоя.

Измерения не позволяют приписать эту разницу самой Studio: исходный фон GPU уже составлял 6 044 MiB, а WDDM не предоставил надёжную атрибуцию VRAM процессам. PyTorch allocator metrics (`memory_allocated`/`memory_reserved`) не собирались. По одному системному прогону нельзя установить, чем именно объясняется небольшое остаточное изменение.

**Вывод:** явная утечка не доказана; значимый лишний расход VRAM, который можно безопасно устранить без изменения модели и синтеза, не обнаружен.

### 5.3. Внешние решения и применимость

Изученные материалы по оптимизации CosyVoice/SGLang в основном направлены на пропускную способность, параллельную обработку запросов, scheduling и ускорение вычислений. Это не готовое решение для снижения idle VRAM в локальном приложении с одной постоянно загруженной моделью и последовательной генерацией.

Изменение точности/весов, квантование, перенос модели, изменение параметров синтеза и замена runtime выходят за согласованные ограничения задачи. Поэтому эти направления не применяются.

### 5.4. Финальное решение

- Оставить текущую загрузку CosyVoice в GPU при старте и прогрев без изменений.
- Не менять `clear_vram()`, жизненный цикл модели, синтез и обработку WAV.
- Не добавлять opt-in сбор allocator metrics и не повторять аппаратный прогон: дальнейшая диагностика не оправдана без нового конкретного симптома.
- Не менять portable runtime, Python, CUDA, PyTorch, модель или её точность.
- Возвращаться к исследованию только при воспроизводимом росте VRAM, нехватке памяти либо другой подтверждённой проблеме.

**Что не менялось:** production-код, runtime, модель, конфиги, API, WAV, OBS, Streamer.bot и DonationAlerts.

**Проверки:** владелец выполнил системный baseline на RTX 5080; добавленные тесты прошли GitHub Actions CI. Это не является полноценным CUDA/CosyVoice runtime-тестом на целевой Windows-машине. Повторные аппаратные измерения не проводились.

## 6. Откат и безопасность

Изменения этого закрытия затрагивают только документацию. При необходимости их можно отменить отдельным revert-коммитом; откат кода приложения или runtime не требуется.

Не использовать force push, reset или rebase.
