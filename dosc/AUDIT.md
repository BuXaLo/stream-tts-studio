# Отчёт аудита и эксплуатационная оценка

**Дата обновления:** 2026-11-08  
**Ветка:** `dev`  
**Метод:** статический анализ кода репозитория плюс уточнения владельца об архитектуре поставки и реальной эксплуатации.

## 1. Контекст, который меняет оценку

Репозиторий содержит только код приложения. Portable Python, ядро CosyVoice, ML-модули, модели и инструменты поставляются отдельно архивом; приложение накладывается поверх этого изолированного окружения. Целевой режим — локальный Windows-ПК, связка OBS + Streamer.bot.

Владелец подтвердил, что генерация аудио и интеграционный тракт испытаны многими часами реальных стримов и сейчас работают. Это эксплуатационная информация от владельца, а не независимое воспроизведение аудита. Она означает, что текущую архитектуру и пользовательские сценарии следует сохранять, а не переписывать ради стилистических предпочтений.

## 2. Главный вывод

Нет оснований считать приложение нестабильным или рекомендовать замену runtime. Статический анализ выявляет отдельные места, где можно повысить безопасность и устойчивость. Приоритет — узкие исправления на границах недоверенного ввода и секретов, без вмешательства в TTS engine и интеграционные контракты.

## 3. Находки и актуальность

### A-01 — Небезопасная вставка текста в OBS Overlay
**Приоритет: высокий для входящего недоверенного текста.**  
В `web/overlay/overlay.js` текст реплики в некоторых режимах анимации формируется как HTML и вставляется через `innerHTML`. Если в сообщение попадёт HTML/JS payload, это может привести к DOM XSS в контексте OBS Browser Source.

**Предлагаемое исправление:** формировать DOM-узлы и текстовые узлы через `createElement`/`textContent`, сохранив классы, порядок слов, анимации и тайминги. Это наиболее изолированное улучшение.

### A-02 — API без авторизации и wildcard CORS
**Приоритет: средний в локальном loopback-сценарии; высокий при доступности из LAN.**  
Код допускает wildcard CORS и не имеет полноценной API-аутентификации. По умолчанию сервер слушает loopback, что существенно ограничивает сетевую экспозицию. Однако локальные процессы и веб-страницы могут пытаться обращаться к localhost; wildcard CORS не является желательным default. При bind на LAN риск значительно возрастает.

**Предлагаемое исправление:** сначала подтвердить фактические origins Dashboard/Overlay и все интеграционные клиенты. Затем вводить совместимый локальный access token только для тех вызовов, которые могут менять состояние или запускать действия. OBS и Streamer.bot должны получить токен без ручного вмешательства в эфирный сценарий. Не включать авторизацию «одним коммитом» без теста всех клиентов.

### A-03 — Секрет DonationAlerts в API-ответе
**Приоритет: высокий.**  
GET `/api/da/config` возвращает объект настроек целиком, который может содержать `client_secret`. Это ненужное раскрытие секрета любому клиенту, имеющему доступ к endpoint. OAuth tokens сохраняются в локальном JSON.

**Предлагаемое исправление:** GET должен возвращать признак наличия секрета, но не само значение. Сохранение нового секрета — только при явной передаче нового значения. UI должен отображать «секрет сохранён», не очищая его при обычном сохранении остальных настроек. Изменение протестировать на сценариях подключения, повторного открытия настроек и обновления токена.

### A-04 — OAuth state не проверяется
**Приоритет: средний.**  
OAuth callback не проверяет одноразовый state. Рекомендуется добавить случайный state с TTL и проверкой callback. Нужно проверить полный цикл авторизации и повторную авторизацию DonationAlerts.

### A-05 — Синхронный HTTP внутри async worker
**Приоритет: низкий/условный для текущей эксплуатации.**  
В async worker используются синхронные `requests`. Это потенциально блокирует event loop на время сетевого ожидания. Само по себе это не доказывает наблюдаемые задержки или проблемы в текущем рабочем сценарии.

**Рекомендация:** не менять только ради «асинхронности». Сначала измерить задержки/пропуски событий. Если проблема подтверждена, заменить сетевой слой отдельным изменением с сохранением retry, timeout и reconnect semantics.

### A-06 — Лимиты загрузок и валидация параметров
**Приоритет: средний для устойчивости.**  
Нужны ограничения на размер/длительность аудио и диапазоны параметров обработки, чтобы ошибочный или чрезмерный ввод не приводил к высокому расходу RAM/VRAM. В локальной модели угроз риск ниже, чем у публичного сервиса, но защита от случайно выбранного огромного файла полезна.

**Рекомендация:** определить лимиты на основе реальных пользовательских файлов и возможностей целевого ПК. Не вводить произвольные маленькие ограничения, которые могут отрезать штатные workflow.

### A-07 — HTML в OAuth callback
**Приоритет: средний.**  
Параметры ошибки OAuth вставляются в HTML-ответ. Следует экранировать текст, сохранив понятное сообщение и поведение callback.

### A-08 — Монолитный backend
**Приоритет: низкий, сопровождаемость.**  
`server/app.py` объединяет несколько ответственностей. Это усложняет навигацию и тестирование, но не является само по себе уязвимостью и не мешает подтверждённой текущей эксплуатации.

**Рекомендация:** не делать большой рефакторинг в рамках hardening. Выделять компоненты только по мере появления тестов и конкретной задачи.

### A-09 — Нет тестов/CI и манифеста в видимом Git-дереве
**Приоритет: процессный, не runtime-дефект.**  
Отсутствие таких файлов в репозитории не означает, что приложение не тестировалось: владелец сообщил о длительной практической эксплуатации. Однако автоматические регрессионные проверки нужны, чтобы безопасно менять код. Инвентаризацию версий portable archive вести отдельно от Python-манифеста приложения.

## 4. Порядок исправлений

1. Overlay text rendering: устранить HTML injection без визуальных изменений.
2. OAuth callback escaping.
3. Скрыть client secret в GET API и адаптировать UI к маскированному значению.
4. Добавить OAuth state с проверкой полного потока.
5. Определить и ввести обоснованные upload/parameter limits.
6. Рассмотреть локальную авторизацию и CORS после инвентаризации клиентов.
7. Только при наличии измерений — менять async worker/network layer.
8. Архитектурный рефакторинг — последним, небольшими шагами.

## 5. Что уже подтверждено, а что нет

- **Со слов владельца:** генерация аудио, OBS и Streamer.bot работают в реальной длительной эксплуатации.
- **Статически по коду:** перечисленные конкретные места потенциального риска и текущие API/DOM-паттерны.
- **Не проверялось в рамках этого аудита:** повторный запуск приложения, целевая GPU/CUDA-конфигурация, содержимое portable archive, нагрузка, реальные OAuth-провайдеры и полный эфирный end-to-end сценарий.

Нельзя использовать этот статический отчёт как основание для обновления Python/CUDA/PyTorch/CosyVoice или замены portable archive.
