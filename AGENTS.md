# AGENTS.md — инструкции для AI-агентов и разработчиков

Этот файл задаёт обязательные правила работы с репозиторием **BuXaLo/stream-tts-studio**. При конфликте с удобством реализации приоритет имеют сохранение рабочего функционала и безопасность данных пользователя.

## 1. Назначение проекта и модель поставки

Stream TTS Studio — локальное Windows-приложение для TTS/voice cloning на базе CosyVoice 3, ориентированное на OBS и Streamer.bot, с интеграцией DonationAlerts.

**Git-репозиторий содержит прикладной код Studio, а не полный runtime-дистрибутив.** Python, portable-окружение, ядро CosyVoice, ML-библиотеки, модели, FFmpeg и другие инструменты поставляются отдельно большим архивом. Код приложения накладывается поверх подготовленного изолированного окружения.

Из этого следуют правила:

- Не предполагать, что portable runtime или модели присутствуют в Git checkout.
- Не устанавливать зависимости в системный Python и не заменять portable Python.
- Не обновлять, не пересобирать и не модифицировать отдельный runtime archive без прямого отдельного поручения.
- Не менять версии Python, CUDA, PyTorch, torchaudio, CosyVoice, ONNX Runtime, FFmpeg или моделей «заодно» с изменениями приложения.
- Не добавлять крупные модели, runtime-бинарники, архивы, пользовательские аудио и секреты в Git.

## 2. Критически важное требование: не ломать работающий функционал

Приложение используется локально на ПК во время стримов. Владелец подтвердил длительную практическую эксплуатацию: генерация аудио и связка OBS + Streamer.bot работают в реальных эфирах.

Существующая рабочая версия — baseline, который нужно сохранять. Любое изменение должно быть минимальным, проверяемым и обратимым.

Без отдельного согласования запрещено менять:

- запуск через существующий `start_server.bat` и использование portable Python;
- публичные HTTP routes, методы, обязательные поля, JSON-ключи и типы ответов;
- контракт `POST /speak`, формат/передачу WAV и поведение генерации;
- WebSocket endpoint `/ws/overlay`, структуру событий и payload;
- URL и настройки OBS Browser Source;
- генерируемые C# Actions, адреса и параметры Streamer.bot, способ воспроизведения WAV;
- OAuth callback URL и работающий пользовательский сценарий DonationAlerts;
- форматы и расположение пользовательских конфигов, персонажей, голосовых референсов, аватаров, тем и шрифтов.

Если изменение контракта действительно необходимо, сначала опиши причину, совместимый переходный период, миграцию, тесты и откат; дождись согласования.

## 3. Git и ветвление

- Основная рабочая ветка проекта — **`dev`**.
- Все изменения по умолчанию выполняй только в `dev`.
- **Никогда не коммить и не пушь в `main`**, не создавай PR/merge в `main` и не меняй default branch без прямого поручения владельца.
- Перед началом работы проверь текущую ветку, чистоту рабочего дерева и актуальность `dev`.
- Не перезаписывай чужие изменения и не используй force push.
- Не делай reset/rebase/cherry-pick или массовую историю Git без явного разрешения.
- Делай небольшие логически цельные коммиты с понятными сообщениями.
- Не включай в коммит временные файлы, логи, токены, пользовательские данные, аудио, модели или артефакты runtime.

Если работа ведётся через GitHub API, явно указывай branch `dev`; для обновления существующего файла сначала получай его актуальный SHA из `dev`. После записи повторно прочитай файл и проверь результат.

## 4. Обязательный процесс перед изменением

1. Прочитай этот файл и относящиеся к задаче документы в `dosc/`.
2. Изучи текущую реализацию и все места вызова изменяемого кода.
3. Определи внешние контракты: Dashboard, OBS, Streamer.bot, DonationAlerts, REST и WebSocket.
4. Сформулируй минимальный план и перечисли возможные регрессии.
5. Установи baseline: какие существующие сценарии должны продолжить работать.
6. Если затрагиваются пользовательские данные или форматы — подготовь резервную копию и план восстановления.
7. При недостатке контекста не выдумывай поведение: найди подтверждение в коде или запроси уточнение.

Не начинай с большого рефакторинга. Не смешивай исправление бага, реорганизацию файлов, форматирование и обновление зависимостей в одном изменении.

## 5. Архитектурные ориентиры

- Backend находится преимущественно в `server/app.py`; не считай его размер самостоятельным дефектом.
- Dashboard — статические HTML/CSS/JavaScript файлы в `web/dashboard/`.
- OBS Overlay — `web/overlay/`; его визуальное поведение и анимации являются частью пользовательского контракта.
- Генератор C# для Streamer.bot находится в Dashboard (в частности, `builder.js`).
- TTS engine и ML-инструменты работают из отдельного portable runtime.
- Не переносить ML-инициализацию, не менять порядок генерации и не вводить новый concurrency model без измеримой причины и тестов.
- Не делать приложение сетевым или multi-user сервисом без отдельного запроса. Сохранять локальный сценарий и loopback bind по умолчанию.

## 6. Безопасность

Весь внешний ввод считай недоверенным: текст донатов/чата, имена пользователей, параметры OAuth callback, загружаемые аудио/изображения/шрифты и запросы локальных клиентов.

Обязательные практики:

- Для отображения пользовательского текста использовать безопасные DOM API (`textContent`, создание узлов), а не конкатенацию HTML с последующим `innerHTML`.
- Экранировать внешние значения при формировании HTML-ответов.
- Не возвращать client secrets, access/refresh tokens и другие credentials в API-ответах.
- Не выводить секреты, OAuth tokens и персональные данные в логи, ошибки, тестовые fixtures и коммиты.
- Не очищать сохранённый секрет при обычном сохранении формы с пустым password-полем.
- Проверять OAuth state и входные параметры в рамках совместимого изменения OAuth flow.
- Проверять тип, размер и содержимое загружаемых файлов; ограничения выбирать по реальным поддерживаемым сценариям, не вводить произвольные малые лимиты.
- Сохранять bind на `127.0.0.1`, если иное явно не согласовано.
- Не считать CORS заменой аутентификации. Перед изменением CORS/auth составить список всех клиентов, включая OBS Browser Source и Streamer.bot, и проверить совместимость.

Не добавляй новые внешние зависимости, если задачу можно решить средствами текущего стека. Любое добавление зависимости должно быть обосновано и проверено на совместимость с portable runtime; не выполнять автоматическое обновление всего окружения.

## 7. Тестирование и проверка

Не заявляй, что тесты или запуск выполнены, если фактически их не запускал. Отделяй статический анализ от runtime-проверки.

Для изменений используй подходящие проверки:

### Backend / API
- Проверить сохранение прежних routes, методов, payload и кодов ответов.
- Проверить обработку валидного и некорректного ввода.
- Для TTS orchestration использовать mock engine там, где GPU/runtime недоступны.
- Не считать mock-тест доказательством успешного GPU-инференса.

### Overlay / frontend
- Проверить обычный русский/английский текст, emoji, переносы строк и HTML-символы.
- Проверить payload вида `<img src=x onerror=alert(1)>`: он должен отображаться буквально, без выполнения.
- Проверить все режимы анимации, темы, аватары, preview и очистку предыдущей реплики.
- Убедиться, что структура WebSocket payload не изменилась.

### Интеграции
- Проверить Streamer.bot Action, получение WAV и воспроизведение.
- Проверить OBS Browser Source и WebSocket reconnect.
- Проверить DonationAlerts OAuth, получение тестового события и вызов Streamer.bot.
- Не использовать реальные донаты для теста, если доступен тестовый сценарий.

### Runtime / выпуск
- Для изменений, затрагивающих запуск или генерацию, нужен smoke test на копии целевой Windows portable-установки с тем же runtime archive.
- Не проводить первые испытания на рабочем эфире.
- После каждого этапа повторять прежний baseline checklist.
- Если portable runtime недоступен, явно отметить соответствующую проверку как невыполненную.

## 8. Обновление данных и конфигурации

- Не удалять, не переименовывать и не пересоздавать существующие пользовательские JSON-файлы.
- Не менять схему конфигурации без необходимости.
- Если миграция необходима: сделать её отдельным шагом, сохранить резервную копию, обеспечить безопасное поведение при повторном запуске и документировать откат.
- Запись важных JSON выполнять атомарно, если это можно внедрить без нарушения текущего поведения.
- Не включать реальные пользовательские данные в fixtures; использовать синтетические примеры.

## 9. Документация

Документация проекта находится в `dosc/` (имя каталога намеренное; не переименовывать без запроса).

При изменении поведения обновляй соответствующие документы:

- `dosc/ARCHITECTURE.md` — архитектура и потоки данных;
- `dosc/API.md` — публичные API и payloads;
- `dosc/AUDIT.md` — подтверждённые находки и ограничения аудита;
- `dosc/SECURITY.md` — модель угроз и меры защиты;
- `dosc/OPERATIONS.md` — установка, эксплуатация, резервирование и откат;
- `dosc/ROADMAP.md` — согласованный план работ.

Чётко различай:
- факт, подтверждённый исходниками;
- эксплуатационное свидетельство владельца;
- гипотезу/потенциальный риск;
- проверку, реально выполненную в текущей среде.

Не описывай потенциальное замечание статического анализа как доказанную runtime-уязвимость. Не утверждай, что portable archive проверен, если его содержимое не было доступно.

## 10. Формат выполнения задачи и отчёта

Для каждой задачи:

1. Кратко описать цель и затрагиваемые файлы.
2. Указать потенциальное влияние на совместимость.
3. Внести минимальные изменения только в `dev`.
4. Выполнить доступные проверки и перечислить их результаты.
5. Повторно проверить diff и отсутствие секретов/пользовательских данных.
6. Обновить документацию, если поведение или инструкции изменились.
7. Сообщить commit SHA и ссылки на изменённые файлы.

В итоговом отчёте явно перечислить:
- что изменено;
- что намеренно не менялось;
- какие тесты пройдены;
- какие тесты не запускались и почему;
- риски и способ отката.

## 11. Запрещённые действия без отдельного разрешения

- Изменять `main` или сливать `dev` в `main`.
- Обновлять/заменять portable runtime, модели, CUDA/PyTorch или ML-библиотеки.
- Переписывать TTS pipeline или менять поведение генерации «для чистоты архитектуры».
- Массово рефакторить `server/app.py` без регрессионных тестов.
- Менять API/WS/Streamer.bot/OBS contracts без согласования.
- Менять форматы пользовательских данных без миграции и backup.
- Удалять функции, настройки, темы, анимации или совместимость со старыми конфигами ради упрощения.
- Запускать destructive команды, удалять рабочие данные или публиковать секреты.
- Заявлять о runtime-успехе на основании только чтения кода или mock-тестов.

**Главный принцип:** улучшать приложение вокруг проверенного рабочего ядра, а не подвергать риску сам рабочий эфирный тракт.
