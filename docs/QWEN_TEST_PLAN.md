# План экспериментальной сборки Qwen3-TTS для Stream TTS Studio

**Статус:** планирование, код и runtime ещё не переносились.  
**Экспериментальная ветка:** `qwen_test`  
**База ветки:** `dev_test` — `824b2d9c5c3743a4748cf42c5c84ff23e27bd5f7`  
**Движок:** [qwentts.cpp](https://github.com/ServeurpersoCom/qwentts.cpp)  
**Цель:** собрать в отдельной папке независимое окружение Qwen3-TTS 1.7B, затем перенести поверх него копию Studio и адаптировать её отдельно, сохранив текущую CosyVoice-сборку нетронутой.

---

## 1. Принципы и границы эксперимента

1. Это параллельный эксперимент, а не замена текущего CosyVoice 3.
2. Не изменять существующую рабочую сборку, её portable Python, модели, CUDA/PyTorch и runtime.
3. Новую сборку разворачивать в отдельной папке с нуля.
4. Не копировать Python-пакеты из текущего окружения. Установить отдельный CPython и свежие совместимые зависимости.
5. Сначала проверить движок и вспомогательные инструменты автономно. Только после этого переносить код Studio.
6. Адаптацию Studio выполнять в ветке `qwen_test`, не смешивая её с основной разработкой.
7. Сохранять существующие внешние контракты и интеграции: `POST /speak`, WAV, WebSocket `/ws/overlay`, OBS Browser Source, C# для Streamer.bot, OAuth DonationAlerts, конфиги и форматы пользовательских данных.
8. Не переносить CosyVoice, PyTorch, torchaudio и Demucs, если отдельная проверенная необходимость не появится.
9. Не фиксировать версии зависимостей и оборудования на основании предположений. Перед установкой сверить актуальные требования проектов и совместимость пакетов.

## 3. Выбранная конфигурация Qwen

Для первого сравнительного прогона:

- Модель: Qwen3-TTS 1.7B Base, режим клонирования голоса по аудиореференсу и его транскрипции.
- Начальная квантовка: Q8_0.
- Talker: `qwen-talker-1.7b-base-Q8_0.gguf`.
- Audio tokenizer/codec: `qwen-tokenizer-12hz-Q8_0.gguf`.
- Исполняемые программы qwentts.cpp: `tts-server.exe`, `qwen-codec.exe`, `qwen-tts.exe`.
- Основной способ интеграции со Studio: отдельный локальный HTTP-сервис `tts-server.exe`, а не ctypes/DLL.

CustomVoice и VoiceDesign в первый этап не включать: основной сценарий эксперимента — клонирование голосов персонажей.

Размеры GGUF-файлов и доступность конкретных сборок перепроверить непосредственно перед загрузкой. Размер файла не равен расходу VRAM.

## 4. Этапы развёртывания с нуля

### Этап A. Инструменты Windows и CUDA

Установить и проверить:

- актуальный NVIDIA Driver;
- CUDA Toolkit с поддержкой целевой GPU и требуемой архитектуры;
- Visual Studio Build Tools / MSVC C++;
- CMake;
- Ninja;
- Git с поддержкой submodules.

Проверить версии и доступность инструментов из консоли. Убедиться, что CUDA-компилятор и MSVC обнаруживаются сборочной системой.

У qwentts.cpp есть Windows build scripts, но перед запуском проверить жёстко заданные в них пути к Visual Studio/CUDA. Если скрипт не соответствует установленной конфигурации, использовать документированную конфигурацию CMake без внесения ненужных изменений в исходники движка.

**Критерий готовности:** компилятор и CUDA корректно определяются; известны версии всех инструментов.

### Этап B. Независимый Python runtime

1. Выбрать поддерживаемую версию CPython x64 после проверки совместимости всего нужного набора библиотек.
2. Установить Python внутрь новой папки.
3. Создать отдельное виртуальное окружение.
4. Обновить pip и инструменты сборки Python-пакетов.
5. Установить только зависимости, необходимые Studio и вспомогательным компонентам.
6. Проверить, что запуск использует локальный Python/venv, а не системную установку.

Python 3.13 рассматривался как кандидат, но окончательную версию выбрать после проверки матриц совместимости FastAPI, pywebview и Faster-Whisper/CTranslate2. Не переносить автоматически зафиксированный в старой сборке Python 3.10.11.

**Критерий готовности:** чистое окружение создаётся и запускает тестовый Python-код без обращения к старому runtime.

### Этап C. Сборка qwentts.cpp

1. Получить репозиторий с submodules.
2. Зафиксировать commit qwentts.cpp и commit GGML.
3. Настроить Release-сборку с CUDA.
4. Собрать необходимые бинарники.
5. Проверить наличие и запуск `tts-server.exe`, `qwen-codec.exe`, `qwen-tts.exe`.
6. Выполнить предусмотренные проектом тесты, включая ABI-тест, если он входит в текущую версию.
7. Проверить, что бинарники запускаются независимо от Python.
8. Записать версии компилятора, CUDA, CMake, Ninja, параметры сборки и SHA исходников.

**Критерий готовности:** движок собран под Windows с CUDA, бинарники запускаются и видят GPU.

### Этап D. Модели и автономная генерация

1. Скачать выбранные GGUF-модели Qwen3-TTS 1.7B Base Q8_0 из проверенного источника.
2. Проверить контрольные суммы, если опубликованы, и фактические размеры файлов.
3. Выполнить тестовую генерацию через `qwen-tts.exe`.
4. Подготовить голосовой референс и транскрипцию.
5. Проверить кодирование референса через `qwen-codec.exe`.
6. Проверить генерацию с использованием полученных voice latents (`.spk` / `.rvq`, согласно фактическому формату текущей версии).
7. Сохранить тестовые входы, выходные WAV и параметры запуска.

**Критерий готовности:** Qwen генерирует русскую речь и воспроизводимо использует референс без запуска Studio.

### Этап E. HTTP-сервис Qwen

Запустить `tts-server.exe` как отдельный локальный процесс, слушающий только loopback-интерфейс.

Проверить документированные текущей версией endpoints:

- `GET /health`;
- `GET /v1/models`;
- `GET /v1/audio/voices`;
- регистрацию голоса через `POST /v1/audio/voices`;
- удаление голоса через `DELETE /v1/audio/voices/{name}`;
- синтез через `POST /v1/audio/speech`.

Проверить:
- обычный WAV-ответ;
- потоковый режим и формат PCM, если он нужен для дальнейшей интеграции;
- повторное использование зарегистрированного голоса;
- поведение после перезапуска сервера;
- сериализацию нескольких запросов и обработку ошибок;
- время загрузки модели, время регистрации голоса, задержку до первого аудиофрагмента, полное время генерации;
- RAM и VRAM в простое и под нагрузкой.

Уточнить фактическое поведение хранения голосов в текущей версии сервера. Если регистрации хранятся только в памяти процесса, предусмотреть повторную регистрацию при запуске.

**Критерий готовности:** локальный HTTP API стабильно принимает запросы и возвращает пригодный WAV.

### Этап F. FFmpeg и Faster-Whisper

**FFmpeg**

- Установить отдельный Windows build в `runtime/tools/`.
- Не использовать FFmpeg из старой сборки.
- Проверить версию, кодеки и основные команды, которые использует Studio.

**Faster-Whisper**

- Установить свежую совместимую версию в новый venv.
- Модель хранить локально в `runtime/models/`.
- Начальный профиль — CPU, INT8, модель small (если качество и скорость на тестовых данных приемлемы).
- Проверить распознавание без PyTorch и без зависимости от CUDA PyTorch.
- Проверить работу с локально загруженной моделью без обязательного скачивания при каждом запуске.

Demucs на первом этапе не устанавливать: он не требуется для базового сценария. Возвращаться к нему только при подтверждённой необходимости.

**Критерий готовности:** FFmpeg выполняет аудиооперации, Faster-Whisper распознаёт речь на CPU в новом окружении.

## 5. Русская текстовая нормализация

В эксперимент включить только один внешний текстовый нормализатор — **ru-normalizr**: [NickZaitsev/ru-normalizr](https://github.com/NickZaitsev/ru-normalizr).

Исключить из плана:
- rutextnorm;
- RUAccent;
- отдельную автоматическую расстановку ударений.

Задача эксперимента — сравнить внешний текстовый нормализатор с уже имеющейся встроенной нормализацией Studio. Не считать заранее, что внешний вариант лучше.

Подготовить единый набор тестовых фраз из реальных сценариев стрима:
- целые и дробные числа;
- даты и время;
- суммы и валюты;
- проценты и единицы измерения;
- сокращения;
- URL и латиница;
- обычные фразы и длинные сообщения.

Для каждой фразы сохранить три варианта:
1. исходный текст;
2. результат встроенной нормализации Studio;
3. результат ru-normalizr.

Сравнить преобразования и прослушать синтез обоих нормализованных вариантов на одном движке и одном голосе. Проверить поддержку пользовательских правил/словарей и возможность отключения нормализатора.

**Критерий готовности:** принято обоснованное решение — оставить встроенную нормализацию, заменить её либо использовать внешний нормализатор как дополнительный этап.

## 6. Совместимость WAV-конвертации

Текущий Studio helper `convert_to_clean_wav()` приводит аудио к:

- WAV;
- mono;
- 24 kHz;
- PCM signed 16-bit.

Предварительно этот формат подходит для входного референса Qwen. При этом qwentts.cpp умеет принимать ряд других WAV-форматов и самостоятельно приводить вход к внутреннему формату. Поэтому предварительная конвертация для самого Qwen может быть необязательной.

На первом этапе не менять существующий helper. Провести сравнение трёх вариантов на одинаковых исходниках:

1. WAV после текущего `convert_to_clean_wav()`;
2. исходный WAV без предварительной конвертации;
3. WAV, преобразованный FFmpeg напрямую по параметрам, рекомендованным текущей версией qwentts.cpp.

Проверить:
- mono и stereo;
- стерео, где голос присутствует только в правом канале;
- разные частоты дискретизации;
- PCM16 и поддерживаемые движком альтернативные форматы;
- тихие и громкие референсы;
- длительность, обрезку, клиппинг и качество клонирования.

**Предварительное решение:** сохранить текущую конвертацию как общий канонический формат для сопоставимого тестирования CosyVoice и Qwen. Отказываться от неё только если тесты покажут измеримую пользу прямой подачи исходного файла.

## 7. Перенос Studio поверх подготовленного runtime

Перенос выполнять только после успешного завершения автономных этапов A–F.

1. Использовать код из `dev_test` на базовом commit `824b2d9c5c3743a4748cf42c5c84ff23e27bd5f7`.
2. Перенести код приложения, web UI и необходимые ресурсы.
3. Не переносить старый CosyVoice runtime, старый Python, старые site-packages, PyTorch и модели.
4. Пользовательские данные переносить отдельно и выборочно: персонажи, пресеты, активный персонаж, настройки, шрифты и другие необходимые данные.
5. Секреты и токены DonationAlerts не включать в Git и не выводить в логах.
6. Проверить пути к Python, FFmpeg, моделям, бинарникам и пользовательским данным.
7. Сохранить резервную копию исходных пользовательских данных.

Важно: простое копирование кода не сделает Studio запускаемой в новом окружении. Текущий `server/app.py` импортирует Torch и загружает CosyVoice; эти зависимости необходимо убрать или изолировать в ходе последующей адаптации.

## 8. План адаптации кода Studio

Основные затрагиваемые участки (точный diff готовить только после повторного чтения актуального кода в ветке):

| Компонент | Направление адаптации |
|---|---|
| `server/app.py` | Убрать обязательную загрузку CosyVoice/Torch; организовать запуск и контроль Qwen-сервиса |
| `studio/core/env.py` | Новые пути к Python runtime, FFmpeg, моделям и qwentts |
| `studio/services/tts_engine.py` | HTTP-адаптер к qwentts.cpp |
| `studio/services/text.py` | Сравнение встроенной и внешней нормализации |
| `studio/routes/tools.py` | Faster-Whisper CPU без PyTorch |
| `studio/routes/characters.py` и связанные сервисы | Сохранение референсов и управление регистрацией/латентами голосов |

Не менять без необходимости:
- внешний контракт `POST /speak` и формат WAV;
- WebSocket `/ws/overlay`;
- OBS Browser Source;
- генерируемый C# для Streamer.bot;
- OAuth DonationAlerts;
- существующие форматы конфигов и данных;
- интерфейс аудиоредактора и его историю обработки.

Особое внимание:
- Текущий параметр скорости CosyVoice может не иметь прямого аналога в API qwentts.cpp. Проверить доступные параметры; если потребуется, применять FFmpeg `atempo` после генерации с сохранением текущего поведения сегментации и пауз.
- Сохранить текущую сегментацию текста и сборку аудиофрагментов, чтобы сравнение движков не смешивалось с изменением логики Studio.
- Проверить повторную регистрацию голосов после перезапуска Qwen-сервера.
- Не допускать одновременного запуска двух копий сервера на одном порту.

## 9. Сравнительное тестирование CosyVoice и Qwen

Использовать одинаковые:
- текстовые сообщения;
- референсы и транскрипции;
- настройки громкости и скорости, насколько параметры сопоставимы;
- условия записи и воспроизведения.

Набор фраз должен включать короткие, длинные, эмоциональные и нейтральные реплики, даты, суммы, время, проценты, сложные числительные и неоднозначные русские слова.

Измерять:
- время загрузки модели;
- время до первого аудиофрагмента;
- полное время генерации;
- RTF;
- RAM и VRAM;
- качество тембра и сходство с референсом;
- дикцию, ударения, интонацию и паузы;
- стабильность длинных запросов;
- поведение при серии запросов и ошибках.

Не переносить benchmark-цифры из README как гарантированные результаты. Фиксировать реальные результаты на целевой машине с указанием оборудования и версий.
