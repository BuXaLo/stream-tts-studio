# План безопасной реализации улучшений

## Цель и неизменяемые условия

Цель — устранить конкретные риски и повысить устойчивость, **не нарушив работающую генерацию и интеграцию OBS + Streamer.bot**.

Неизменяемые условия:
- не менять portable archive, portable Python, CUDA, PyTorch, CosyVoice, модели и версии runtime;
- сохранять совместимость обоих способов запуска: рекомендуемый `start_studio.bat` (Launcher/tray) и резервный `start_server.bat` (консольный backend);
- не менять существующие REST routes, методы, JSON-поля и типы ответов без отдельного согласования;
- не менять WebSocket endpoint/event schema и OBS Browser Source URL;
- не менять генерируемые C# Actions, Streamer.bot endpoints и воспроизведение WAV;
- не менять пути/форматы конфигов, персонажей, голосовых референсов и тем без обратимой миграции;
- не внедрять изменения во время эфира.

## Этап 1 — безопасный рендер текста Overlay — выполнено

Реализация безопасного вывода пользовательского текста выполнена в Overlay и Dashboard; backend перед отправкой события заменяет URL на «ссылка». Контракт WebSocket сохранён.

Исторические критерии проверки:
- убрать интерпретацию внешнего текста как HTML;
- использовать DOM nodes и `textContent`;
- сохранить все существующие режимы анимации, классы, CSS, порядок слов, длительности и fallback;
- не менять формат WebSocket payload и backend.

Проверки:
- обычный русский/английский текст;
- символы `< > & " '`, emoji, переносы строк;
- payload вроде `<img src=x onerror=alert(1)>` отображается как буквальный текст;
- каждый режим анимации, тема, аватар и preview работают как раньше;
- OBS Browser Source отображает текст и очищает предыдущую реплику.

**Откат:** вернуть только предыдущую версию overlay.js.

## Этап 2 — безопасный OAuth callback — выполнено

HTML callback экранирует внешние значения (`error`, ответ token endpoint и исключения) через `html.escape`; одноразовый OAuth `state` имеет TTL 10 минут и проверяется в callback.

Исторические критерии проверки:
- экранировать все внешние значения, попадающие в HTML;
- сохранить route, query semantics и понятный результат для пользователя.

Проверить успешную авторизацию, отказ/ошибку OAuth и строки с HTML-символами. Откат — один файл.

## Этап 3 — защита DonationAlerts secret — выполнено

GET `/api/da/config` не раскрывает сохранённый secret и возвращает флаг `client_secret_set`. Пустое/отсутствующее значение при сохранении не затирает ранее сохранённый secret.

Исторические критерии проверки:
- GET не возвращает фактический `client_secret`, только статус наличия;
- пустое поле в UI при загрузке означает «секрет уже сохранён», а не «удалить секрет»;
- новый секрет записывается только при явном вводе/замене;
- существующий сохранённый secret/token не очищается обычным сохранением других настроек.

Перед изменением сохранить копию `da_config.json` и `da_tokens.json`. Проверить: открыть настройки, изменить несекретное поле, сохранить, перезапустить, проверить OAuth refresh и тестовый donation flow. Не менять имена ключей на диске без необходимости.

## Этап 4 — OAuth state — выполнено

Реализовано: случайный state хранится в памяти с TTL 10 минут и удаляется при callback-проверке. Проверка полного OAuth flow в целевом DonationAlerts-аккаунте остаётся частью локальной приёмки.

## Этап 6 — локальная API защита и CORS (частично выполнено)

Реализована нормализованная same-origin проверка для изменяющих HTTP-запросов и WebSocket при наличии `Origin`; запросы небраузерных клиентов без `Origin` сохраняют совместимость. Полноценная API-аутентификация/локальный токен не внедрялись: это отдельное решение после инвентаризации всех клиентов. Launcher endpoints слушают только loopback.

## Этап 8 — жизненный цикл сбора startup-журнала Monitor — выполнено

**Цель:** показывать в Monitor относящиеся к текущему запуску и остановке события, не превращая Monitor в постоянный поток runtime-логов.

**Реализованное поведение:**
1. Monitor читает `startup.log` через `/startup-log?offset=N`, используя byte offset. Позиция чтения сохраняется между циклами backend в течение жизни Monitor.
2. Во время запуска Monitor собирает startup-сообщения. Сбор завершается после готовности backend и подтверждения состояния DonationAlerts: если DA выключен — после подтверждения `enabled === false`; если включён — после подключения и появления сообщения `Подключено к DA Centrifugo`.
3. После достижения критерия готовности Monitor выполняет финальное чтение и приостанавливает polling `/startup-log`. Опрос `/launcher-status` продолжается.
4. При остановке backend через Monitor сбор возобновляется, чтобы получить относящиеся к остановке сообщения. Launcher дожидается завершения backend и сбрасывает лог, после чего Monitor выполняет финальное чтение хвоста.
5. При следующем запуске backend в том же окне Monitor чтение возобновляется с сохранённого byte offset. Старые строки повторно не подтягиваются; история и счётчики Monitor в рамках текущей сессии сохраняются.
6. На время HTTP-запроса `/launcher-stop` polling статуса не должен преждевременно завершить сбор по состоянию stopped/error. После ответа Launcher выполняется финальное чтение журнала.

**Что намеренно не менялось:**
- Непрерывная запись `startup.log`, включая перенаправление stdout/stderr backend.
- Прямой консольный запуск через `start_server.bat`.
- `studio.log`, WebSocket/`MonitorLogHandler`, классификация уровней, фильтрация AMP warning, буферы, счётчики и лимиты событий.
- REST/WebSocket-контракты, `/speak`, WAV, OBS Browser Source и генерируемые C# Actions.

**Техническое решение:** для разделения циклов используется byte offset чтения, а не отключение записи в файл. Промежуточный pipe с переключаемой записью stdout/stderr, описанный в прежней редакции плана, не реализовывался: он не нужен для текущего поведения и потребовал бы более широкого вмешательства в процесс запуска backend.

**Связанные коммиты реализации:**
- `55f2ecc9e6b7a4d3e11d78ddd586911862e82db1` — возобновление сбора startup.log между перезапусками backend.
- `4035a79e0b444711cfacc71cad19881da90dd73f` — регрессионная фиксация жизненного цикла сбора в Monitor.

**Проверки и ограничения:**
- Пользователь вручную проверил завершение Studio через Monitor и повторный запуск без закрытия Monitor: строки остановки и нового запуска отображаются корректно.
- Добавлены тесты на lifecycle Launcher, byte offset и возобновление сбора. Тест lifecycle возобновления проверяет статические условия в JS; он не воспроизводит конкурентные HTTP-запросы.
- Полноценный запуск pytest в целевой Windows-среде и отдельная проверка аварийного завершения backend не подтверждены.

**Статус:** реализация этапа выполнена; расширенную проверку аварийных сценариев и Windows-регрессии проводить при следующем тестовом проходе.

## Правила релиза каждого этапа

1. Один логически цельный набор изменений — отдельный commit в согласованной рабочей ветке (сейчас `dev_test`).
2. До изменения — baseline tests; после — те же tests плюс новые регрессионные.
3. Сверить diff: никаких незапланированных изменений runtime, API, JSON schema или generated actions.
4. Smoke test по [OPERATIONS.md](OPERATIONS.md).
5. Только после успешного теста переходить к следующему этапу.
6. Не объединять несколько этапов в один большой PR. Не мержить в `main` автоматически.

## Критерии приёмки

- Все существующие пользовательские сценарии проходят до и после изменений.
- Генерация WAV и её latency не ухудшились сверх заранее согласованного допуска.
- Streamer.bot получает тот же ответный формат и воспроизводит аудио.
- OBS Overlay сохраняет визуальный вид/анимации и корректно отображает произвольный текст как текст.
- DonationAlerts сохраняет авторизацию и доставку событий; secret не раскрывается в GET.
- Конфиги, персонажи, референсы и пользовательские темы сохранены.
- Проверки проведены на копии реальной portable установки до использования в эфире.
