# Запуск, эксплуатация и восстановление

## 1. Модель установки

Установка состоит из двух частей:
1. отдельный архив с portable Python, CosyVoice core, ML-библиотеками, моделями, FFmpeg и инструментами;
2. Git-код Stream TTS Studio, который накладывается поверх подготовленной основы.

Portable-окружение изолировано; приложение не должно зависеть от системного Python или произвольно установленных системных библиотек. При обновлении кода не обновлять runtime архив автоматически.

### Зафиксированная конфигурация portable runtime

Подтверждённая конфигурация рабочей установки:

- Python: `3.10.11`
- TTS-модель: `FunAudioLLM/Fun-CosyVoice3-0.5B-2512` (релиз 2025/12)
- Локальный каталог модели: `cosyvoice3/pretrained_models/Fun-CosyVoice3-0.5B`
- Официальный источник модели: https://huggingface.co/FunAudioLLM/Fun-CosyVoice3-0.5B-2512

SHA256 четырёх основных файлов модели сверены с официальными LFS-хешами Hugging Face и совпали:

| Файл | SHA256 |
|---|---|
| `llm.pt` | `69f43bd545131c30e98947fb360ea8b4dc9916d8e83dded7757c7ea4f5a24970` |
| `flow.pt` | `a6fab32a7825e5b0bc855ddd948f8db9370b0a786fbc249caa4595e95b608e4b` |
| `hift.pt` | `b279d7641eb97ae55b3b540cfba4f953c26492a2df758328a89a4d007ab87a65` |
| `speech_tokenizer_v3.onnx` | `23236a74175dbdda47afc66dbadd5bcb41303c467a57c261cb8539ad9db9208d` |

Эти значения фиксируют проверенную рабочую установку, а не требование автоматически обновлять runtime. При замене Python, модели или ML-зависимостей выполнять отдельную проверку совместимости и сохранять предыдущую рабочую копию.

## 2. Запуск

Рекомендуемый запуск — корневой `start_studio.bat`: он запускает `server\launcher.pyw` через portable `pythonw.exe`, создаёт обязательный системный трей, запускает backend через portable `python.exe` и выбирает режим окна монитора. Основной режим — `pywebview` на WebView2; если пакет или WebView2 Runtime недоступен, Launcher использует Edge с `--app=`, а при отсутствии Edge — браузер по умолчанию. Если `python.exe` или `pythonw.exe` отсутствует, батник переключается на резервный `start_server.bat`. Прямой `start_server.bat` запускает `server\app.py` через portable `python.exe` с консольным выводом.

Backend по умолчанию доступен на `http://127.0.0.1:8765`; Dashboard — `/dashboard`, Overlay — `/overlay`.
### Автоматическое открытие Dashboard

- При прямом запуске через `start_server.bat` Dashboard автоматически открывается после готовности backend, если в настройках включено «Открывать Dashboard при запуске» (`auto_open_browser`).
- При запуске через `start_studio.bat` автоматически открывается Monitor. Dashboard не открывается автоматически независимо от значения `auto_open_browser`; его можно открыть через пункт «Открыть Dashboard» в меню системного трея.
- Это намеренное разделение режимов: настройка `auto_open_browser` управляет обычным запуском backend без Launcher/Monitor.
 Для OBS Browser Source использовать текущий URL и параметры, настроенные в рабочем профиле.

## 3. Данные, которые нужно сохранять

| `server/config.json` | Host, port, параметры генерации и browser flag |

Расположение может зависеть от версии/сборки. Перед копированием сверять фактические пути установки. Не коммитить пользовательские конфиги, токены, голосовые файлы или модели в публичный репозиторий.

## 4. Безопасная процедура обновления

Перед каждым обновлением:
1. Завершить текущий эфир и штатно остановить приложение.
2. Сделать копию всей рабочей папки или как минимум кода, runtime-конфигов, `characters/`, пользовательских шрифтов и portable archive (если обновляется отдельно).
3. Зафиксировать текущие версии/хеши portable archive и текущий commit кода.
4. Накатить только небольшой набор изменений приложения из согласованной рабочей ветки (для текущей работы — `dev_ui_test`).
5. Запустить выбранный режим тем же BAT-файлом (`start_studio.bat` или `start_server.bat`), которым будет пользоваться оператор.
6. Выполнить smoke checklist ниже.
7. Только после успешной проверки использовать обновление в эфире.

Не обновлять одновременно код приложения и portable runtime: иначе при регрессии будет трудно определить источник. Для обычного изменения кода portable archive должен оставаться неизменным.

## 5. Smoke checklist перед эфиром

- [ ] `start_studio.bat` создаёт значок трея, открывает монитор и запускает backend; либо `start_server.bat` запускает backend в консоли.
- [ ] Dashboard открывается, список персонажей и настройки загружаются.
- [ ] Выбор персонажа сохраняется и применяется.
- [ ] Тестовая генерация возвращает корректный WAV.
- [ ] Streamer.bot action отправляет запрос и воспроизводит WAV.
- [ ] OBS Browser Source подключается к Overlay.
- [ ] Тестовая реплика отображается с нужной темой, аватаром и анимацией.
- [ ] Текст с символами `< > & " '` отображается буквально, не как HTML.
- [ ] DonationAlerts подключается, тестовое событие проходит в Streamer.bot.
- [ ] Нет ошибок в логах и заметного роста задержки генерации.

Проверки DonationAlerts выполнять с тестовым событием, а не реальным донатом, если доступен такой режим.

## 6. Откат

Если smoke test не пройден:
1. остановить backend;
2. вернуть предыдущую копию кода целиком;
3. восстановить конфиги/данные только если они были изменены миграцией;
4. оставить portable archive прежним;
5. повторить smoke checklist на прежней версии.

Не удалять и не пересоздавать персонажей, токены или JSON при откате исправления, если конкретное изменение не требовало миграции.

## 7. Логи и журналы

- `logs/studio.log` — основной лог приложения с ротацией (2 MiB, 3 backup-файла).
- `logs/streamerbot_failed_donations.jsonl` — неудачные передачи донатов в Streamer.bot; не публиковать файл без проверки на персональные данные.
- JSON-хранилища поддерживают одно поколение резервных копий `*.bak`; временные `*.tmp` создаются рядом с целевым файлом и удаляются после операции.

## 8. Диагностика

- Backend не стартует: проверить наличие portable Python по ожидаемому пути и целостность runtime archive.
- Модель не загружается: сверить версии и файлы portable CosyVoice/PyTorch/CUDA с известной рабочей сборкой.
- Ошибка генерации: проверить персонажа, voice reference, свободную VRAM и временные каталоги.
- Не работает Overlay: проверить URL Browser Source, локальный порт и WebSocket.
- Не проходят донаты: проверить OAuth status, соединение DonationAlerts и доступность Streamer.bot `/DoAction`.
- FFmpeg операция не работает: проверить portable FFmpeg и его путь внутри runtime archive.

### Предупреждение ONNX Runtime о CUDAExecutionProvider

В Windows portable-окружении при загрузке CosyVoice 3 может появляться предупреждение вида:

```text
Specified provider 'CUDAExecutionProvider' is not in available provider names.
Available providers: 'AzureExecutionProvider, CPUExecutionProvider'
```

Для текущей конфигурации это ожидаемо и само по себе не означает ошибку генерации или неисправность GPU:

- В используемом наборе зависимостей GPU-вариант `onnxruntime-gpu==1.18.0` предназначен только для Linux; для Windows/macOS предусмотрен `onnxruntime==1.18.0`.
- Поэтому в Windows `onnxruntime` не предоставляет `CUDAExecutionProvider`. Компонент, который запрашивает CUDA provider, использует доступный fallback, обычно CPU.
- PyTorch — отдельная подсистема. Если `torch.cuda.is_available()` возвращает `True`, это подтверждает доступность GPU для PyTorch, но не добавляет CUDA provider в ONNX Runtime.
- В проектном коде нет прямых вызовов `onnxruntime`, `InferenceSession` или `CUDAExecutionProvider`. CosyVoice загружается через внешний runtime-каталог `cosyvoice3`; источник запроса находится в CosyVoice или его зависимостях.
- faster-whisper в проекте запускается через CTranslate2 на CUDA, когда PyTorch сообщает о доступности GPU. Его Silero VAD использует ONNX Runtime на CPU штатно.

**Текущие действия:** если CosyVoice успешно загружается, генерации проходят без ошибок и производительность устраивает, предупреждение считать информационным для текущей Windows-конфигурации. Не требуется менять код, переустанавливать ONNX Runtime, CUDA, PyTorch или portable-окружение только ради устранения этого сообщения. Не устанавливать `onnxruntime-gpu` поверх текущей среды без отдельной проверки совместимости всего runtime.

Если появятся реальные ошибки генерации, проблемы загрузки модели или подтверждённое ухудшение производительности, диагностировать их отдельно по полному traceback и фактическому использованию CPU/GPU. Само это предупреждение не является достаточным основанием для изменений.

## 9. Ограничение сетевой экспозиции

Сохранять bind на `127.0.0.1`, если нет явной необходимости в LAN-доступе. Не выставлять API в интернет. Любое изменение host/CORS/auth проверять отдельно со всеми локальными клиентами.


## Launcher, монитор и завершение работы

- Для обычной работы используйте `start_studio.bat`. Он запускает Launcher через portable `pythonw.exe`; Launcher создаёт обязательный трей, выбирает окно монитора и запускает backend отдельным процессом через portable `python.exe`. Основной режим — `pywebview` + WebView2; запасные режимы — Edge (`--app`) и браузер по умолчанию.
- Если `python.exe` или `pythonw.exe` отсутствует, `start_studio.bat` вызывает `start_server.bat` как резервный консольный режим. Ошибка создания трея не приводит к тихому запуску без трея: Launcher завершает запуск с диагностикой.
- `start_server.bat` — прямой консольный запуск backend без Launcher/tray. Используйте его для диагностики или старого режима. Не запускайте оба режима одновременно.
- В основном режиме `pywebview` крестик скрывает окно, не останавливая backend или Launcher. Повторно открыть то же окно можно двойным щелчком по значку трея или через меню значка. В Edge/browser fallback окно закрывается вручную; закрытие внешнего окна само по себе не завершает Launcher или backend.
- В меню трея доступны «Открыть монитор», «Открыть Dashboard» (браузер по умолчанию) и «Выход». При выборе «Выход» Launcher передаёт монитору сигнал закрытия через `/launcher-status`, после чего окно закрывается, а Launcher штатно останавливает backend. Кнопка в мониторе запускает backend, если он остановлен, или вызывает штатное выключение, если работает.
- При штатном выключении Launcher использует `/launcher-stop`, который вызывает backend shutdown endpoint; Uvicorn прекращает принимать новые подключения, ожидает активные запросы в пределах graceful timeout и выполняет shutdown-хуки.
- `logs/startup.log` содержит ранние сообщения Launcher/backend и traceback; `logs/studio.log` — основной журнал приложения. Ошибки создания трея не скрывать и не обходить.
- При старте на Windows создаётся именованный mutex для защиты от второго экземпляра Launcher.
- При выборе «Выход» Launcher закрывает окно монитора и штатно останавливает backend. Если окно `pywebview` не загрузилось за 25 секунд, включается запасной режим; если оно не закрылось за 20 секунд после команды выхода, запускается аварийная процедура завершения с остановкой backend.
- Причина выбора режима записывается в `logs/startup.log`: «Режим окна монитора: pywebview …» либо «Режим окна монитора: Edge/браузер (причина)».

### WebView2 и необязательные Python-пакеты

Для основного режима нужны WebView2 Runtime (это отдельный компонент, не сам браузер Edge) и следующие пакеты в portable-окружении `cosyvoice3\upy`:

```bat
cosyvoice3\upy\python.exe -m pip install --no-deps pywebview==6.2.1 pythonnet==3.1.0 clr_loader==0.3.1 proxy_tools==0.1.0 bottle==0.13.4
```

Установка необязательна: если пакетов или WebView2 Runtime нет, Launcher автоматически переходит к Edge/browser fallback. Пакеты устанавливаются именно в portable Python; не используйте системный Python и не обновляйте зависимости runtime заодно.

Чтобы принудительно отключить `pywebview` для одного запуска, выполните в том же окне CMD:

```bat
set "STUDIO_MONITOR_WINDOW=browser"
start_studio.bat
```

Переменная должна быть установлена в окружении CMD, из которого запускается BAT-файл. Она наследуется Launcher и не записывается в конфиги. Чтобы вернуться к автоматическому выбору, откройте новое окно CMD или выполните `set "STUDIO_MONITOR_WINDOW="`.

При диагностике сначала изучайте `logs/startup.log`, затем `logs/studio.log`.


### Отображение журнала запуска и остановки в Monitor

При запуске через `start_studio.bat` Monitor показывает новые строки `logs/startup.log` во время запуска backend. После достижения штатного критерия готовности backend и DonationAlerts чтение приостанавливается, но уже показанная история остаётся в Monitor.

При ручном выключении кнопкой Monitor чтение возобновляется и продолжается до завершения `/launcher-stop`. Launcher дожидается завершения backend и записывает итоговую строку с кодом завершения; после ответа Monitor дочитывает оставшийся хвост журнала. Поэтому строки shutdown-последовательности должны отображаться в том же цикле остановки, а не только при следующем запуске.

При повторном запуске backend в том же Monitor сбор начинается снова с сохранённой byte offset-позиции. Старые записи и счётчики не очищаются. Полное завершение самого Launcher/Monitor завершает и эту сессию отображения.

Для диагностики учитывайте назначение файлов: `logs/startup.log` содержит ранние сообщения Launcher/backend и хвост штатного завершения, а `logs/studio.log` остаётся основным журналом приложения. Эта функция Monitor не заменяет файловые журналы и не меняет прямой консольный режим `start_server.bat`.
