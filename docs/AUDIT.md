# Отчёт аудита и эксплуатационная оценка

**Дата обновления:** 2026-11-16  
**Ветка:** `dev_test`; кодовая ревизия, по которой сверялись находки: `f502d7e2f29d38414c5ee2eb0f577514b1515cab`. Документационные исправления внесены отдельными коммитами после этой ревизии.  
**Метод:** статический анализ кода репозитория плюс уточнения владельца об архитектуре поставки и эксплуатации. Ручные проверки обозначены как подтверждённые владельцем.

## 1. Контекст, который меняет оценку

Репозиторий содержит только код приложения. Portable Python, ядро CosyVoice, ML-модули, модели и инструменты поставляются отдельно архивом; приложение накладывается поверх этого изолированного окружения. Целевой режим — локальный Windows-ПК, связка OBS + Streamer.bot.

Владелец подтвердил, что генерация аудио и интеграционный тракт испытаны многими часами реальных стримов и сейчас работают. Это эксплуатационная информация от владельца, а не независимое воспроизведение аудита. Она означает, что текущую архитектуру и пользовательские сценарии следует сохранять, а не переписывать ради стилистических предпочтений.

## 2. Главный вывод

Нет оснований считать приложение нестабильным или рекомендовать замену runtime. Статический анализ выявляет отдельные места, где можно повысить безопасность и устойчивость. Приоритет — узкие исправления на границах недоверенного ввода и секретов, без вмешательства в TTS engine и интеграционные контракты.

## 3. Находки и актуальность

### A-01 — Безопасный вывод текста в OBS Overlay
**Статус: исправлено.**

Текст реплики в `web/overlay/overlay.js` создаётся через DOM-узлы и `textContent`; пользовательский текст не интерпретируется как HTML. В `innerHTML` остаётся только очистка контейнера (`""`), а не вставка содержимого сообщения. Регрессионные проверки безопасного рендера присутствуют.

### A-02 — Локальная API-аутентификация (неактуально для текущего продукта)
<badge>Неважно / не требуется сейчас</badge>

**Решение владельца:** полноценная API-аутентификация и локальный access token избыточны для текущего локального portable-приложения. Не реализовывать и не считать незакрытой задачей до выхода продукта на внешний рынок.

Текущие меры остаются достаточными для согласованного сценария: backend по умолчанию слушает loopback (127.0.0.1), wildcard CORS отсутствует, для изменяющих HTTP-запросов и WebSocket при наличии `Origin` действует нормализованная same-origin проверка, Launcher endpoints слушают только loopback.

**Условие пересмотра:** возвращаться к вопросу только если появится hosted/cloud-режим, доступ через интернет или изменится согласованная модель сетевого использования. Сам факт бесплатного распространения локальной portable-версии не является основанием внедрять API-токен. Режим `0.0.0.0` остаётся сетевой экспозицией без аутентификации и не должен считаться защищённым для недоверенной LAN.

### A-03 — Секрет DonationAlerts в API-ответе
**Статус: исправлено.**

GET `/api/da/config` не возвращает сохранённое значение `client_secret`, а сообщает только `client_secret_set`. Пустое или отсутствующее поле в POST не затирает ранее сохранённый секрет. Это подтверждено текущей реализацией и тестами.

### A-04 — OAuth state — исправлено и проверено
**Статус: выполнено; полный OAuth flow DonationAlerts подтверждён владельцем.**

OAuth callback использует случайный одноразовый `state` с TTL 10 минут и проверяет его при возврате от провайдера. Владелец подтвердил успешное прохождение OAuth-подключения DonationAlerts в целевой установке. Дополнительная проверка полного flow не является открытой задачей.

### A-05 — Синхронные HTTP-вызовы в DonationAlerts worker
**Статус: исправлено в согласованном объёме.**

Синхронные HTTP-вызовы worker выполняются через `asyncio.to_thread(...)`, поэтому сетевое ожидание не блокирует event loop. Существующие retry, timeout и reconnect semantics сохранены. Переписывать сетевой слой на другой HTTP-клиент без подтверждённой проблемы не требуется.

### A-06 — Лимиты загрузок и валидация параметров
**Статус: искусственные upload limits сознательно не планируются.**

Параметры обработки валидируются, FFmpeg ограничен timeout 120 секунд. Владелец решил не вводить искусственные ceilings по размеру и длительности аудио: пользователь должен иметь возможность выбрать нужный фрагмент из длинной записи. Это осознанное продуктовое решение, а не незакрытая задача. Очень большие файлы по-прежнему могут расходовать значительные RAM и временное место на диске; возвращаться к лимитам только при подтверждённой проблеме реального workflow.

### A-07 — HTML в OAuth callback
**Статус: исправлено.**

Внешние `error`, тело ответа и текст исключения экранируются через `html.escape` перед включением в HTML callback.

### A-08 — Разделение backend
**Статус: выполнено в `dev_test`.**  
Backend разнесён по `server/studio/core/`, `server/studio/services/` и `server/studio/routes/`. `server/app.py` оставлен bootstrap/entrypoint и подключает роутеры. Контракт маршрутов и граф импортов покрыты регрессионными тестами. Дальнейшее дробление не требуется без конкретной задачи.

### A-09 — Тесты, CI и манифест portable runtime
**Статус: тесты и CI добавлены; runtime manifest по-прежнему отдельный.**  
В актуальном Git-дереве присутствуют `tests/` и `.github/workflows/tests.yml`; GitHub Actions выполняет Python compileall/pytest и JavaScript syntax checks. Portable runtime поставляется отдельно, поэтому его версии и модели не следует выводить из Git-манифеста приложения. Инвентаризацию portable archive вести отдельно.

## 7. Жизненный цикл startup.log в Monitor (2026-11-13)

В `dev_test` доработан сбор `logs/startup.log` в Monitor для последовательных циклов запуска и ручной остановки backend.

- Monitor возобновляет чтение перед новым запуском backend и при ручном Stop.
- Чтение использует byte offset; offset и накопленная история не сбрасываются между backend-циклами в рамках жизни Monitor.
- При запуске чтение приостанавливается после достижения существующего критерия готовности backend/DonationAlerts.
- При ручной остановке введён барьер по завершению HTTP-запроса `/launcher-stop`: периодический опрос статуса не должен завершать сбор раньше ответа. После ответа выполняется финальное чтение журнала, включая строки завершения backend.
- Запись в `startup.log` остаётся непрерывной; механизм не заменяет stdout/stderr backend и не затрагивает `studio.log`, API генерации, WAV или Overlay WebSocket.

Связанные коммиты реализации:
- [55f2ecc9](https://github.com/BuXaLo/stream-tts-studio/commit/55f2ecc9e6b7a4d3e11d78ddd586911862e82db1) — возобновление сбора startup log между backend-циклами и финальное дочитывание.
- [4035a79e](https://github.com/BuXaLo/stream-tts-studio/commit/4035a79e0b444711cfacc71cad19881da90dd73f) — тест жизненного цикла сбора, сохранения offset и истории.

Покрытие: в `tests/test_launcher.py` проверяются чтение журнала по byte offset и статические условия переходов состояния Monitor. Последний тест проверяет наличие необходимых защитных конструкций в JavaScript, но не является полноценным моделированием конкурентных HTTP-запросов.

Эксплуатационная проверка владельца: ручной запуск и остановка студии из Monitor проверены; строки запуска и завершения отображаются в соответствующих циклах. В рамках этой актуализации документации повторный Windows-запуск тестов и отдельная проверка аварийного завершения процесса не выполнялись. Не следует считать их подтверждёнными только на основании статического анализа.

## A-10 — Диапазон speed персонажа и согласованность с /speak (2026-11-16)

**Статус: закрыто в согласованном объёме; реализация проверена владельцем.**

Ранее выявленное расхождение устранено в `dev_test`:

- UI-ползунок скорости персонажа расширен до диапазона **0.5–2.0x** с шагом 0.05.
- `api_save_character()` ограничивает обычные числовые значения при сохранении пресета: ниже 0.5 сохраняется 0.5, выше 2.0 — 2.0.
- В `POST /speak` явно переданный `speed` имеет приоритет над скоростью пресета и ограничивается диапазоном 0.5–2.0. Если поле не передано, используется значение `speed` выбранного персонажа из пресета.

Штатный UI не формирует такие значения; расширять обработку нештатных внешних входных данных владелец не считает необходимым. Это осознанная граница задачи, а не заявление о полной валидации любых возможных входных значений.

### Проверка владельца

Владелец вручную подтвердил:
- ползунок UI достигает 2.0x;
- значение скорости корректно сохраняется в пресете;
- при явном указании скорости в запросе используется переданное значение;
- при отсутствии поля `speed` используется скорость из пресета персонажа.

**Итог:** исходное расхождение между UI, сохранением пресета и штатным использованием скорости закрыто. Возвращаться к пункту только при появлении конкретной воспроизводимой проблемы в обычном сценарии.

### A-11 — числовые форматы в TTS-тексте не сохраняются (открытая функциональная ошибка)

В разделе «Решения владельца» в [REFACTOR_PLAN.md](REFACTOR_PLAN.md) зафиксировано, что значения с `%`, десятичные числа (`3.5`), порядковые (`1-й`), время (`12:30`) и разделённые пробелом разряды (`1 000`) должны оставаться без изменения.

Текущая регулярка `(?<![A-Za-z0-9_])\d+(?![A-Za-z0-9_])` в `sanitize_text()` рассматривает каждую группу цифр между пунктуацией или пробелами как отдельное число. Поэтому перечисленные форматы преобразуются частями, например: `3.5` → `три.пять`, `1-й` → `один-й`, `12:30` → `двенадцать:тридцать`, `1 000` → `один ноль ноль ноль`, `25%` → `двадцать пять%`.

Тесты `tests/test_text.py` покрывают обычные целые и длинные последовательности цифр, но не эти форматы. **Статус: не решено, не отложено.** Если зафиксированное решение владельца остаётся в силе, до релиза требуется узкое исправление нормализации и регрессионные тесты. В рамках данного аудита код не менялся.

### Операционные уточнения
